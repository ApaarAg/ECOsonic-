## 2. Integration architecture

`POST /api/v1/analyses` streams the original upload into per-analysis storage, enforces the configured **50 MiB** limit, checks the extension/header/audio, and queues a background job. The worker runs the real `BirdNetEngine` through `AnalysisPipeline` and `BirdNetEngineAdapter`:

1. Validate the stored source and its signal.
2. Decode with FFmpeg and write a PCM WAV at **32,000 Hz, mono**. The source upload is retained.
3. Run BirdNET V3.0 FP32 prediction on that normalized WAV, using one inference worker.
4. Extract embeddings from the same normalized WAV; validate float32, finite `(N, 1280)` vectors and segment times.
5. Save the `.npy` atomically and publish detection rows, embedding-segment rows, metrics, paths, and `completed` status in one final database transaction.

Model initialization is guarded by a lock and happens once at application startup. Failure to initialize the production model aborts startup. The mock engine is only selected by explicit test fixtures; there is no production fallback to fabricated results. The configured GPU preference selects CUDA when available, while `BirdNetEngine` retains CPU provider fallback. The Windows CUDA DLL path setup is conditional on Windows.

Result and detection endpoints return HTTP 409 while an analysis is not complete. This prevents clients from observing partial results. On a job error, the worker records `failed:<stage>` and a safe error summary, rolls back unpublished rows, removes a partial embedding file, and retains the original audio. Startup marks previously queued or processing jobs failed with `failed:process_restart` so interrupted work is visible.

### Detection mapping

The original `species_name` text is preserved in `class_label`; BirdNET's `start_time`, `end_time`, and `confidence` become the backend seconds and confidence fields. Labels formatted as `scientific name_common name` are split into those two fields. A bounded set of recognized non-animal sound labels is marked `sound_class`; labels remain unmodified. The app does not supply a taxonomy dataset, so `taxon_group` is explicitly `Unknown` rather than guessed, and geo scores remain null.

### Persistence and path safety

- SQLite stores analyses, detections, and embedding segment metadata; foreign keys are enabled on SQLite connections.
- Vector data stays in NumPy `.npy` files, not SQLite. Segment rows carry vector index, timestamps, parent analysis ID, and an overlapping detection ID where one exists.
- Raw uploads are kept under a generated UUID directory and the client filename is reduced to a basename. Processed and embedding paths are generated by storage code from the analysis UUID.
- Temporary NPY output is written beside the destination and atomically replaced; pickle loading is disabled. Test fixtures use a temporary SQLite database and temporary storage tree, removed after the run.

Measurements are from the final API acceptance run on the Windows workstation with BirdNET 1.5.0, FP32 V3.0, ONNX Runtime GPU 1.26.0, and the RTX 4060 Laptop GPU. The model loaded once for the test process; measured initialization was about 0.72 seconds. Peak process RSS was approximately 382–386 MB.

Those are not directly comparable to the Phase 2 end-to-end path: Phase 2 includes normalized WAV processing and runs with a different runtime setup and API/database work. No speedup claim is made. The normalized Cicada result's strongest Ash Cicada window is 6–9 s at 0.9139; Phase 1's strongest was 18–21 s at 0.9534, and Phase 2 still reports the same class at 18–21 s at 0.8856. The changed input resampling path is a plausible source of score/ranking differences, but this run does not isolate the cause. These recordings are smoke-test inputs, not labelled accuracy ground truth.

## 7. Frontend integration contract

1. Upload multipart form data to `POST /api/v1/analyses` with field `file`. Optional form fields are `latitude`, `longitude`, `recorded_at`, and `model_version`. A successful request returns HTTP 202 and an analysis object containing `id`.
2. Poll `GET /api/v1/analyses/{id}` (or `/status` for the compact status response). Read `status`, `progress`, and `current_stage`. Expected stages are `queued`, `validating_audio`, `preprocessing`, `birdnet_inference`, `saving_detections`, `extracting_embeddings`, `saving_embeddings`, and `completed`.
3. On `completed`, fetch `GET /api/v1/analyses/{id}/results` for metrics, detections, embedding shape/dtype, and segment metadata. `GET /api/v1/analyses/{id}/detections` returns detections alone. Both endpoints return HTTP 409 before completion.
4. On `failed`, display `error_message` and `current_stage`; the source upload remains available for debugging. `GET /api/v1/analyses/{id}/embeddings/download` downloads the NPY array when a client needs the binary vectors.

The `taxon_group` can currently be `Unknown`; do not present it as a verified family/order. Display the original `class_label` and confidence as returned.
